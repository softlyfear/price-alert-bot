# price-alert-bot

Telegram-бот отслеживания цен на товары Wildberries и Ozon. Пользователь добавляет товар и задаёт цену-порог; когда цена доходит до порога, бот присылает уведомление.

## Что делает бот

Команды бота:

| Команда | Что делает |
|---|---|
| `/start` | приветствие и список команд |
| `/help` | подробнее о боте |
| `/add` | добавить товар в отслеживание |
| `/list` | мои товары и пороги; карточка товара, удаление порога или товара |
| `/cancel` | отменить текущее действие |

Диалог `/add` идёт шаг за шагом:

1. Ссылка на товар Wildberries или Ozon либо артикул Wildberries (только цифры).
2. Бот отвечает репликой «Проверяю товар», пока получает данные, и затем показывает карточку: название и текущую цену.
3. Вы вводите порог в рублях (например, `1990` или `1990,50`).
4. Бот показывает итог, вы нажимаете «Подтвердить» или «Отмена».

Направление порога выбирается автоматически: порог ниже текущей цены — сообщить, когда станет дешевле; выше — когда станет дороже. Порог, равный текущей цене, отклоняется с просьбой ввести другой.

После срабатывания порог остаётся активным; повторное уведомление приходит не чаще, чем раз в cooldown. По умолчанию цены проверяются раз в 15 минут (`APP__SCHEDULER_INTERVAL_SECONDS`), cooldown — сутки (`APP__ALERT_COOLDOWN_SECONDS`), лимит — 50 товаров на пользователя (`APP__MAX_PRODUCTS_PER_USER`).

Бот отслеживает цену без персональных скидок маркетплейса (кошелёк, карта, баллы и т. п.): на сайте цена для вас может быть ниже. Об этом бот напоминает везде, где показывает цену.

## Статус маркетплейсов

Работа бота в эксплуатации не подтверждена: проверка с сервера эксплуатации живым прогоном не выполнялась.

- **Wildberries.** Цена берётся с использованием токена антибота, который получает Chromium внутри контейнера. Работоспособность с сервера эксплуатации живым прогоном не подтверждена. Если получить токен не удалось, пользователь видит честное сообщение о блокировке, а не «товар не найден».
- **Ozon.** Цена запрашивается через публичный `entrypoint-api`, но Ozon защищён антиботом, и запросы блокируются. Ozon не отдаёт цены; поддержка ждёт отдельной доработки. Блокировка показывается пользователю как блокировка, а не как «товар не найден».

## Разработка

Нужны Python 3.14 (файл `.python-version`) и [`uv`](https://docs.astral.sh/uv/).

```
make install          # uv sync
make install-browser  # Chromium для Playwright (полный Chromium, не headless shell)
make hooks            # git-хуки: pre-commit, commit-msg, pre-push
make db-upgrade       # применить миграции к базе из .env
make run              # миграции и сервер с автоперезагрузкой
```

Без `make install-browser` интеграционные тесты браузера красные. Остальные цели `make` перечисляет `make help`.

Интеграционные тесты идут на реальном PostgreSQL. Если задана переменная `TEST_DATABASE_URL` (формат `postgresql+asyncpg://...`), берётся эта база, и тесты применяют к ней миграции (`alembic upgrade head`): указывайте только базу, которую не жалко. Иначе тесты сами поднимают одноразовый контейнер PostgreSQL через `testcontainers`, для чего нужен доступный Docker. Нет ни переменной, ни Docker — интеграционные тесты БД пропускаются.

Проверки качества (все пять обязательны перед коммитом):

```
uv run ruff check .
uv run ruff format --check .
uv run mypy app tests
uv run lint-imports
uv run pytest --cov=app --cov-report=term-missing
```

`make fmt` форматирует код и применяет автоисправления `ruff`, `make type` запускает `mypy`, `make test-cov` — `pytest` с покрытием.

`WB__BROWSER_SANDBOX=false` (значение в `.env.example`) допустимо только на машине разработки. Без песочницы Chromium скомпрометированная страница Wildberries может прочитать секреты процесса. В эксплуатации — только `true`; стек `docker-compose.yml` задаёт это значение сам.

## Конфигурация

Настройки читаются из переменных окружения; для разработки и стека — из файла `.env` в корне репозитория. Файл создаётся по образцу `.env.example` и в git не попадает (он в `.gitignore`).

Группы переменных:

| Префикс | Что настраивает |
|---|---|
| `TG__` | токен бота (`TG__BOT_TOKEN`) |
| `DB__` | подключение к PostgreSQL (`DB__USER`, `DB__PASSWORD`, `DB__HOST`, `DB__PORT`, `DB__NAME`) и параметры пула |
| `REDIS__` | подключение к Redis (хранилище состояний диалогов); `REDIS__PASSWORD` необязателен |
| `APP__` | интервал проверки, cooldown, лимит товаров, параллелизм и таймаут запросов к маркетплейсам |
| `WB__` | получение токена Wildberries через браузер: таймауты, бюджет запусков, песочница |

Значения по умолчанию и пояснения — в `.env.example` и `app/core/config.py`. Все переменные `DB__` из `.env.example` обязательны (`DB__ECHO`, `DB__POOL_SIZE`, `DB__MAX_OVERFLOW`, `DB__POOL_PRE_PING`, `DB__POOL_RECYCLE`, `DB__AUTOFLUSH`, `DB__EXPIRE_ON_COMMIT` умолчаний не имеют), поэтому `.env` берётся из `.env.example` целиком.

- `DB__ECHO=True` из `.env.example` включает вывод SQL в журнал — только для разработки; в эксплуатации `DB__ECHO=False`.
- Секреты стека (`DB__PASSWORD`, `TG__BOT_TOKEN`) составляйте из символов `[A-Za-z0-9_-]`: `docker compose` и `pydantic-settings` по-разному разбирают `$`, `#`, кавычки и пробелы.
- Вывод `docker compose config` и `docker inspect` содержит значения окружения, то есть секреты. Не пересылайте его и не вставляйте в отчёты.

## Эксплуатация

Стек в `docker-compose.yml`: PostgreSQL, Redis, одноразовый сервис `migrate` и бот `app`. Данные PostgreSQL и Redis лежат в именованных томах. Ни один сервис не публикует порт наружу. Пределы памяти и CPU, время на остановку и остальные числа заданы в `docker-compose.yml` вместе с обоснованием в комментариях.

**Запуск и обновление — только `make docker-up`.** Цель собирает образ, останавливает `app` и поднимает стек. Голый `docker compose up -d` заново применит миграцию при работающем боте, а миграции схемы должны идти при остановленном `app`. Остановка — `make docker-down`, журналы — `make docker-logs`, перезапуск — `make docker-restart`.

**Первый запуск:**

1. Скопируйте `.env.example` в `.env` целиком и заполните токен бота, `DB__USER`, `DB__PASSWORD`, `DB__NAME`. Остальные переменные `DB__` (`DB__ECHO`, поля пула, `DB__AUTOFLUSH`, `DB__EXPIRE_ON_COMMIT`) обязательны: умолчаний у них в `app/core/config.py` нет, без них `app` не стартует. В эксплуатации задайте `DB__ECHO=False`. Хосты и порты PostgreSQL и Redis стек подставляет сам.
2. Выполните `make docker-up`. Сервис `migrate` дожидается готовности PostgreSQL, доводит схему до `head` и завершается; `app` стартует только после его успешного завершения.

**Свой файл окружения:** `make docker-up ENV_FILE=/path/to/file`. Цели `make` передают его и как `--env-file`, и как переменную `ENV_FILE`; при прямом вызове `docker compose …` нужно задать оба.

**Миграции.**

- Обновление схемы идёт отдельным сервисом `migrate` до старта `app`.
- Откат последней ревизии (при остановленном `app`, после `docker compose stop app`): `ENV_FILE=.env docker compose --env-file .env run --rm migrate alembic downgrade -1` (для своего файла подставьте его путь в оба места). На машине разработки — `make db-downgrade`. Порядок: сначала откат выполняется образом с новой ревизией (он содержит её `downgrade`), затем репозиторий переключается на предыдущую ревизию, затем `make docker-up`. Иначе `migrate` снова применит `upgrade head`.
- Ревизия, упавшая на существующих данных (например, `CHECK` на цену), откатывается целиком и данные не правит. Данные вручную не исправляйте — обратитесь к разработчику.
- После провала `migrate` бот стоит до вмешательства: `app` остановлен, схема осталась прежней. Прежний образ после новой сборки остаётся без имени, готового пути отката нет. Чтобы вернуть работающую версию, переключите репозиторий на предыдущую ревизию и выполните `make docker-up`: образ соберётся заново из кеша слоёв.
- Сломанная сборка работающий `app` не трогает: `make docker-up` падает на сборке до остановки бота.

**Ограничения и поведение стека.**

- Пароль PostgreSQL задаётся при создании тома. Смена `DB__PASSWORD` на существующем томе роняет `migrate`: меняйте пароль в самой базе.
- `make clean-all` тома не удаляет; удаление данных — только явной командой оператора.
- Redis без пароля и без опубликованного порта; `REDIS__PASSWORD` для этого стека не задавайте. При аварийной остановке хоста состояния диалогов теряются с последнего снимка Redis: пользователь начинает диалог заново.
- Гибель polling или планировщика завершает процесс, и стек поднимает его политикой рестарта.
- С недействительным токеном или недоступным Telegram `app` перезапускается циклически. Признаки: растущий `RestartCount` у контейнера и в каждом цикле запись `ERROR` «Telegram is not available at startup».
- Healthcheck `app` (`/health`) только наблюдает: Docker не перезапускает `unhealthy`-контейнер, а зависание без гибели задачи `/health` не ловит.
- Браузер в контейнере: песочница Chromium включена принудительно, для неё стек использует собственный профиль seccomp `docker/seccomp-chromium.json`. Если песочница не стартует, получение токена завершается ошибкой, а не запуском без неё.
- Размер образа — около 1,1 ГБ в распакованном виде (по раннеру CI, overlay2; из-за Chromium и его системных библиотек). При хранилище containerd `docker image ls` показывает до ~1,6 ГБ.
- Одна реплика `app`: polling и планировщик рассчитаны на один экземпляр.

## CI

На каждый push в `main` (`.github/workflows/ci.yml`) выполняется:

- **Quality gate:** `ruff check`, `ruff format --check`, `mypy app tests`, `lint-imports`, `pytest` с покрытием `app` и порогом 100. В job есть сервис PostgreSQL (передаётся через `TEST_DATABASE_URL`) и установленный Chromium.
- **Проверка почт ИИ-ассистентов** в истории коммитов (`scripts/check-ai-email`).
- **Скрипты и compose:** `shellcheck --severity=warning scripts/*` и `docker compose config -q` на фиктивных значениях.
- **Образ:** `make docker-build` дважды (пересборка без изменений не меняет ID образа и не оставляет безымянных образов) и дымовые проверки `scripts/smoke-image price-alert-bot`.

Порог покрытия 100 задан только в шаге CI. Без PostgreSQL (нет ни `TEST_DATABASE_URL`, ни Docker) интеграционные тесты БД пропускаются, и шаг краснеет по покрытию; без Chromium падают тесты браузера. В обоих случаях лечится окружением, а не порогом. Локальный прогон `make test-cov` порогом не краснеет.

## Известные ограничения

- Реплика «Проверяю товар» может остаться висеть, если её отправка или правка оборвались по сети, а Telegram сообщение всё же доставил. Повтор сознательно не делается: он дал бы дубль. К тому же классу относится потеря итогового сообщения шага при сетевом сбое.
- Доставка уведомлений не гарантируется. `triggered_at` выставляется только после того, как Telegram принял сообщение. Если процесс остановлен между отправкой и commit или потерян ответ Bot API, уведомление может прийти дважды: повтор будет на следующей проверке, если цена всё ещё за порогом, и cooldown этот дубль не сдерживает. При `TelegramForbiddenError` (пользователь заблокировал бота) уведомление не доставляется.
- Ozon блокирует запросы (см. [Статус маркетплейсов](#статус-маркетплейсов)).
